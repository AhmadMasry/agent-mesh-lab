## How each original search was sent (gh-phrase-check.txt: GH_DEBUG=api, gh 2.101.0)

gh search issues sends a query argument that holds a space as a quoted phrase, ( "graceful shutdown" ), and sends a
single token unquoted, hyphenated or dotted ones included (event-stream, shutdown.min). gh api search/issues sends
q= as written, so a query sent that way is a word search. No record quoted a query on purpose: B-3 writes every query
in double quotes, single words included, and the three scripts pass the query as one argument. So in each record,
every multi-word query was a phrase search and every single-token query was already a word search. Nothing needed
keeping as a phrase by intent. Two of B-3's queries are error-text fragments (no active execution, is in terminal
state); their word searches cover the phrase and return more.

- B-3 (tracker-search.txt, no script): gh search issues and gh search prs, one quoted query each. 20 queries, 17
  multi-word (9 on a2a-go, 8 on a2a-python). The pages list items. No total_count was recorded.
- B-5a (tracker-search.txt, no script): gh search issues, --match title,body, take 1 issues only and take 2 with
  --include-prs. 14 queries, 7 multi-word. Its end table of gh api total_count was a word search, and the file puts
  the gap between that table and the pages down to comment matching. For the multi-word queries the gap is mostly
  phrase against words. Example: in-flight connections read 0 on the take-1 page and 3 issues in the table.
- B-6 (tracker-search.sh and .txt): gh search issues --include-prs -- "<text>", with a gh api total_count beside each
  page. 26 queries, 16 multi-word.
- C-9 (tracker-search.sh and .txt): the same shape as B-6. 15 queries, 11 multi-word.

None of the four searched only words, so all four needed a re-run. Only the multi-word queries were re-run; a
single-token query is sent the same way by both tools. One difference in scope remains: gh search adds
advanced_search=true, and the plain gh api call does not.
