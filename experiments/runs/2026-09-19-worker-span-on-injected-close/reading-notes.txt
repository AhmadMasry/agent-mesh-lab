WHY (iii) IS NOT MARKED -- where the worker departs from the mock. The task was briefed as "mirror what the mock
does with a failed close", whose span keeps the helper's "failed: <err>" text. Measured first, 2026-09-19T18:41:20Z,
with the call made UNCONDITIONAL (the same shape is kept as mutant 3, below): the could-not-hijack span read
    status.code=Error  status.description=""  http.response.status_code=500  lab.injection=close-after-read
The helper had set "injected: close-after-read failed: response writer does not support hijacking" (its unit test
in internal/otel pins that form), and the ended span carries "" instead: the description was REPLACED. The chain,
read in the module cache at the versions above:
    otelhttp v0.71.0 handler.go l.193      span.SetStatus(h.semconv.Status(statusCode)), after the handler returns
    otelhttp v0.71.0 internal/semconv/server.go l.74-75
                                           if code >= 500 { return codes.Error, "" }
    otel sdk v1.46.0 trace/span.go l.220   if s.status.Code > code { return }   -- only a LOWER status is ignored;
                                           l.224-229 then store the new code with its (empty) description
                                           ("overriding previous values set", the method's own comment, l.206-207)
The worker answers a real 500 on that branch, so the instrumentation's Error "" arrives after the helper's and is
equal, not lower. The mock never meets this: its failed close answers the empty 200 of a handler that wrote nothing,
the instrumentation sets Unset, and Unset is lower than Error. No ordering inside the handler changes it (the
instrumentation sets its status after the handler has returned), and the 500 may not change (nothing on the wire
changes).
Ruling of the controller, 2026-09-19: mark only a TAKEN connection. The marking exists to correct a span that
would otherwise misread (200 / Unset for a connection the worker closed). On branch (iii) the span already reads
what happened (500 / Error) and claims no close; an unconditional call would leave lab.injection=close-after-read
beside Error "" on a connection that was never closed, a span that half-claims a close. Changing the shared helper
so that a failure survives was not asked for and would change the mock's span too. The injection is still named
where it always was for that branch: on the ledger's response line, beside the 500, and in the worker's log.
This is not recorded as a gap of otelhttp or of the SDK: replacing an earlier status with a later one that is not
lower is what span.go says it does. Nothing about it was added to the draft under docs/upstream/.

THE LEDGER (rule 5). compare-ledgers.sh extracts the ingress ledger lines the test logged for all five cases from
before-final-test-on-the-parent.txt (ledger-before.txt) and from after.txt (ledger-after.txt), as written, and
compares them byte for byte with ts_arrival and the port of `remote` masked in the comparison only:
ledger-comparison.txt, 10 lines in 5 cases, byte-identical, same order of lines and of keys. The response line of
a taken connection still carries an explicit "status":0. What the port mask covers: on the six lines of a real
connection the port the loopback picked, which differs from run to run; on the four lines served in process
httptest's fixed 192.0.2.1:1234, which does not, and which one pattern masks along with the rest. With a mask for
127.0.0.1 alone (1234 left as written) the two files are byte-identical too (2026-09-19T19:16:31Z). The script's
wording was corrected to say this after the review of 2026-09-19, and ledger-comparison.txt regenerated
(2026-09-19T19:16:53Z); ledger-before.txt and ledger-after.txt came out byte-identical to the first time.
