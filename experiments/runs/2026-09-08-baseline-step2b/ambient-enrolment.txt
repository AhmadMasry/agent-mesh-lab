Ambient enrolment evidence for the two agentgateway proxies added in step 2b.
Captured 2026-09-08 on the kind cluster agent-mesh-lab, after the baseline runs.
The two proxies enrol by different mechanisms, as the two documentation pages
prescribe, and each is proved separately below.

================================================================================
NAMESPACE LABELS -- the two mechanisms start here
================================================================================

$ kubectl get ns agentgateway-system agentgateway-egress lab -L istio.io/dataplane-mode
NAME                  STATUS   AGE   DATAPLANE-MODE
agentgateway-system   Active   22m   ambient
agentgateway-egress   Active   21m   
lab                   Active   26h   ambient

  agentgateway-system is labelled ambient, as the ingress page instructs
  ("kubectl label ns agentgateway-system istio.io/dataplane-mode=ambient --overwrite").
  `make step-2b` runs it between the two Helm installs and the overlay, so the ingress
  proxy pod is created after the label; the page's step of restarting an already-running
  gateway proxy pod was not performed. The order of operations, from the API server:

$ kubectl get ns agentgateway-system -o jsonpath='{range .metadata.managedFields[*]}{.manager} {.operation} {.time}{"\n"}{end}'
helm Apply 2026-09-08T19:50:06Z
kubectl-label Update 2026-09-08T19:51:28Z

$ kubectl -n agentgateway-system get pods -o custom-columns=NAME:.metadata.name,START:.status.startTime
NAME                                    START
agentgateway-864d45549-tbr2j            2026-09-08T19:50:09Z
agentgateway-ingress-6848b5848f-4d5j4   2026-09-08T19:51:49Z

  So the ingress proxy pod started 21 s after the label and the controller pod 79 s
  before it. Both are listed at HBONE in the workload table below, so that table
  records the state of both pods; it does not by itself show that starting after the
  label is what made a restart unnecessary.

  agentgateway-egress is deliberately left unlabelled, as the egress page instructs:
  "By default, leave the agentgateway-egress namespace unlabeled for ambient mode. If
  you do label that namespace with istio.io/dataplane-mode=ambient, make sure the
  waypoint pods opt out with istio.io/dataplane-mode=none; otherwise ztunnel capture
  can conflict with the waypoint's HBONE listener on port 15008." Observed, and not
  asked for in the overlay: the agentgateway controller stamps that opt-out on the
  waypoint pod itself, so the pod would stay uncaptured even if the namespace were
  labelled later. The overlay sets no pod label; this one comes from the controller:

$ kubectl -n agentgateway-egress get pods -L istio.io/dataplane-mode
NAME                          READY   STATUS    RESTARTS   AGE   DATAPLANE-MODE
agw-egress-674bb755bc-9gd66   1/1     Running   0          21m   none

================================================================================
EGRESS -- enrolled as a mesh waypoint with its own Istio identity, NOT captured
================================================================================

The egress waypoint does not join the mesh by ztunnel capture. It is given an
Istio identity by AgentgatewayParameters.spec.istio.enabled, terminates HBONE on
its own 15008 listener, and is bound to the destination by the ServiceEntry's
use-waypoint labels.

$ kubectl -n agentgateway-egress get agentgatewayparameters agw-egress-params -o jsonpath='{.spec}'
{"istio":{"enabled":true},"service":{"spec":{"type":"ClusterIP"}}}
