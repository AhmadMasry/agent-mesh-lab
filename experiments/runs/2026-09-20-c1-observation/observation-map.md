## 2. What this run did not answer, and why

Nothing in §1 is an enforcement reading: no rule was written, because writing one changes the cluster and C-1
observes it. These stay **TO MEASURE**, unchanged from the skeleton's §3 list except where §1 marks a cell C-1:

1. `HTTPRoute` header match on `A2A-Version` separating two requests (C-6) — the header is on the wire, no route uses it.
2. an agentgateway rule on `source.identity` as a count (C-7). C-1 reads the *telemetry* attribute `src.identity`,
   which is not the same thing as the CEL variable a rule is given; only a rule answers that.
3. whether the ztunnel-captured ingress proxy is given any `source.identity`. C-1 narrows it: that proxy records
   none in its log or on its span, on a leg ztunnel reports `mutual_tls`. Whether a rule there would see one is
   still unread.
4. a route-scoped header rule as a count (C-7). 5–7. the body-parse rules, the buffer limit, `messageId`/`taskId`
   through the same parse (C-8). 8. the A2A marking (C-9). 9–11. the ztunnel and istiod policy probes (C-3, C-4, C-5).
   12. a refusing per-operation hook in each SDK (C-10).

What is true of all twelve, and is the brief's own stop condition, is that **each needs a change to the cluster or
a fixture**. The narrower sentence the skeleton carries — "Every *enforcement* cell needs a second operation on the
wire, and no fixture sends one" (`map-skeleton.md` l.65) — is right where it stands, about the enforcement cells,
and widening it to all twelve would be wrong: cell 8, the A2A marking (C-9), needs `appProtocol` set and then *one*
`SendMessage` to show whether `a2a.method` reads it; cell 3, whether the ingress proxy is given a `source.identity`,
needs one request plus a rule or a change to the log template; and the first half of cell 11, the status istiod
writes on an `AuthorizationPolicy` with `targetRefs` to `agw-central`, needs no traffic at all.

Beside them, one reading C-1 could not take without a change: **what the receiver was handed in its request
headers.** Both receivers' ingress ledgers keep `a2a-version` and `content-type` and no other header —
`agents/worker/ingress.go` l.87-88 in Go, `agents/orchestrator/orchestrator/ledger.py` l.72-73 in Python — so
whether either proxy forwards a caller identity to the application cannot be read from the record as it stands.
Reading it needs **a change to each receiver's ingress ledger**, not to one of them: the leg that matters most is
ingress → orchestrator, the only leg here with no `src.identity` at the proxy, and that one terminates at the
Python orchestrator.
