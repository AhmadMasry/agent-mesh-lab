WHAT THIS STEP IS
  Section 4.4 B of the frozen proposal as it is worded: Agent A starts a SendStreamingMessage; Agent B begins model
  work; the proxy on the path is removed; the stream dies; the client sends ONE SubscribeToTask. It is run with the

THE THREE ITEMS CARRIED FROM B-5a, AND WHAT EACH READ HERE
  1. wait_settled. B-5a's first dry repetition found that `make ledgers` can run before the Task and the model call
     settle, because a stream can end long before either does. Its fix is copied here unchanged in behaviour: after
     both Jobs end the driver reads the worker's (or the orchestrator's) and the mock's pod logs -- it SENDS NOTHING
     -- and waits for the executor's terminal state line, then for the mock's invocation line until the arm stamp
     plus N plus 30 s at the latest, with a 180 s ceiling on the whole wait. Both dry repetitions settled at 0.0 s.
  2. The removed proxy's record of the request it cut. B-5a found it incomplete in three different ways depending on
     proxy and method -- no access line at all, a line with NO http.status field, or a line reading http.status=200
     for a stream the client saw fail -- so counts.py carries all three as columns, with the line's duration and the
     POST statuses beside them, and the entries state what each row read.
  3. The redirect check. internal/httpclient.New leaves CheckRedirect at Go's default, so up to ten 3xx answers
     would be FOLLOWED and CLIENT_HOST re-applied to each, and no test pins "a 3xx is not followed" at this tree.
     A removed proxy is when a gateway is likeliest to answer non-2xx, so every repetition records what BOTH of its
     clients saw -- http_status, content_type, the first JSON-RPC error object on the wire, the SDK's error text --
     and the POST round trips each client's own outermost transport carried, which a followed redirect would
     increase; and counts.py reports every non-2xx and every 3xx line in every access log collected. NO CODE WAS
     CHANGED for this here. The entries state that no redirect policy is pinned at this tree.

THE PROXY-LOG TIMESTAMP DEFECT, measured here and already filed by this lab
  agentgateway at the pinned v1.5.0 renders the sub-second part of a log timestamp with its LEADING ZEROS removed,
  so 21:03:04.066706Z is written 21:03:04.66706Z and reads, as written, 600 ms later than it was.
  docs/upstream/agentgateway-access-log-timestamp-leading-zeros.md: filed as agentgateway#3369 (2026-09-07, closed
  2026-09-08), fixed by #3370, first contained in the v1.6.0-alpha.1 prerelease -- v1.5.0 carries it. NOT a new
  rule 11 candidate and no draft is written.
  MEASURED over every proxy log line this step collected: it falls ONLY on the access line's own stamp --
  47 of 400 access lines (11.75 %, which is the 1/10 + 1/100 + ... a uniform microsecond field gives) against
  0 of 1 986 other proxy lines, and 240 of the six-digit fractions end in a zero, so trailing zeros are NOT dropped
  and a fraction shorter than six digits means leading zeros were. 27 of the 80 repetitions carry at least one.
  WHAT counts.py DOES ABOUT IT: it keeps proxy log lines in the order the proxy WROTE them (file order, which is
  what `kubectl logs` gives) instead of sorting by a stamp that can be wrong by up to 900 ms, and it reports any
  figure whose endpoint is such a stamp as "n-a", never as a number, the way a sleep-affected interval is reported,
  with the raw stamps kept verbatim in `dropped_zero_stamps`. NOTHING is corrected: correcting it would be the
  counter deciding what the proxy meant.
  WHEN IT WENT IN, corrected against this task's own phases.txt, which is the accurate record. An earlier version of
  this file said the handling was "decided and written in before the first counted repetition". THAT IS WRONG, and
  the stamps contradict it: phases.txt dates the change 21:34:51Z, by which time row-py-ingress-forced
  (21:02:40Z-21:20:23Z) and row-py-central-graceful (21:20:23Z-21:27:50Z) were COMPLETE and row-go-ingress-forced
  (21:28:03Z-21:45:56Z) was UNDER WAY. The honest statement is therefore: the handling went in AFTER 40 OF THE 80
  COUNTED REPETITIONS HAD RUN, WITH A THIRD ROW IN PROGRESS -- and, as phases.txt itself words it, before any
  committed output. A different and smaller thing, the comment about what `rm_to_new_pod_first_served_ms_h2c` means
  on this step, is the one written before the first counted repetition; the two were run together in this file and
  should not have been. NOTHING IN THIS RECORD DATES THAT SMALLER COMMENT, so no stamp is given for it here: an
  earlier draft of this correction put "21:02" against it, which would have been the same fault this paragraph
  exists to fix.
  WHY THE ORDER BIASES NOTHING, stated rather than assumed. counts.py reads files; it never touches the cluster and
  it produced no committed output until every repetition had run. The raw per-repetition records are rows.sh's, and
  rows.sh did not change at any point in this task -- one sha256 for all 82 repetitions, printed into every
  variant's control.txt. So no repetition was sent under one rule and another under a second: the rule is mechanical

  to all eighty at once when the counter ran at the end. What the late change DID cost is that the defect was found
