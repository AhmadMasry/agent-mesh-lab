## why a second step-3 was still not enough, and what was done about it
The values fix reached the cluster -- the ConfigMap `prometheus` in `telemetry` has
exactly one `global:` key after the second step-3 -- but the server pod did not pick it
up, and `helm upgrade --wait` failed a second time with "Progress deadline exceeded".
The pod was the same one throughout (name unchanged, age 10 m at that point), and its
last log line was timestamped before the second apply:

  18:02:56 level=ERROR ... line 77: field global already set in type config.plain

Two chart facts explain it together, and both are worth having in the record:

  1. This chart puts NO config checksum annotation on the Prometheus server
     Deployment, so a ConfigMap-only change is not a pod-template change and does not
     roll the server. (The collector chart does the opposite: its Deployment carries
     `checksum/config`, which is why the collector picked its configuration up on the
     first apply.) The chart's answer to this is the `configmap-reload` sidecar, which
     this lab disables under scope rule 6 -- so on this route a scrape-configuration
     change needs an explicit restart, exactly as the manifest route already needed
     one. That is now the same on both routes and is stated in the values file.
  2. A CrashLoopBackOff pod backs off for minutes, so the corrected file sitting in its
     mounted volume was not re-read within the Deployment's progress deadline.

Remedy, recorded: one `kubectl -n telemetry rollout restart deploy/prometheus`, then
`make step-3` run a third time so the target itself is the thing that reports exit 0.
No retry logic was added anywhere and no chart value was changed for this.
