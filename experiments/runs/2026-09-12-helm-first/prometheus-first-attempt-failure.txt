## cause
A defect in deploy/step-3-stress/prometheus-values.yaml as first written, not a
property of the chart. The chart's ConfigMap template emits `global:` from
`.Values.server.global`, and then, after the scrape_configs, dumps whatever keys are
LEFT in `serverFiles."prometheus.yml"` with `toYaml`. It unsets only `scrape_configs`
(`{{- $_ := unset $value "scrape_configs"}}`). So a `global` left under serverFiles is
written a SECOND time, and Prometheus refuses the file:

  parsing YAML file /etc/config/prometheus.yml: yaml: unmarshal errors:
    line 77: field global already set in type config.plain

The earlier render check read the head of the rendered prometheus.yml, saw the correct
`global` from server.global, and did not read the tail where the duplicate sits. That
is what the check missed; the chart behaved as its template reads.

Fix: `global` removed from `serverFiles."prometheus.yml"`; it lives only under
`server.global`. `rule_files: []` stays there and is correct -- an empty list is valid
Prometheus configuration and is what the manifest's file has by omission.

This is recorded rather than quietly corrected because the corollary is a chart fact
worth having in the tree: for this chart, `server.global` is the only place the global
block may be given, and `serverFiles."prometheus.yml".global` is additively wrong
rather than ignored.
