## 2. Where it can apply on this topology
  Routes. agw-central's routes lab/worker and lab/orchestrator are HTTPRoutes whose parentRef is the Gateway
  agw-central, sectionName inner-http, told apart by hostname (deploy/step-2-ambient-agw/worker-route.yaml,
  deploy/step-2c-gate2/orchestrator-route.yaml). The lab already has one such route with an AgentgatewayBackend as its
  backendRef: model-via-agw -> AgentgatewayBackend mockllm, spec.static (deploy/step-2b-agw-ingress-egress/
  egress.yaml). So a waypoint route of this form CAN name an AgentgatewayBackend, and traffic a client addresses to
  the Service still reaches the route: ztunnel sends it to agw-central, which selects the route by hostname
  (proxy/gateway.rs l.1490-1510, the HBONE inbound, route selection by listener and VIP). The ingress's routes
  (worker-ingress, orchestrator-ingress) have the same form with the ingress as parent. No client addressing changes
  on either proxy.
  The upstream leg is where it differs, read from source:
    proxy/httpproxy.rs l.2174: SimpleBackend::Opaque -> BackendCall::from_shared(target, policies).
    l.4372-4386 from_shared: transport_override None.
    l.1855-1886 build_transport: HBONE (or Istio legacy mTLS) is used only when transport_override is set; otherwise
      the application transport, here plaintext. l.3171 and l.3224: transport_override is set only on the Service
      path (build_service_call), from the selected workload's protocol.
    client/mod.rs l.452-471 resolve_target: a Target::Hostname is resolved by DNS (CachedResolver) and dialled at
      the returned address; for a Service name that is the ClusterIP.
  So with the backend type, the proxy dials host:port in plaintext at the ClusterIP, where the Service backend today
  dials the selected pod over HBONE.
    - agw-central: its namespace is not enrolled (kubectl get ns, no dataplane-mode label), so nothing captures that
      plaintext on its side. At the agent's side the pod is in ambient under mesh-wide STRICT, and the lab's standing
      plaintext probe from an uncaptured pod is refused at both receivers (curl exit 56, every standard proof since
      2026-09-12). PREDICTED, from source and from that probe, not measured: every request agw-central forwards to
      an A2A backend naming an agent is refused at the agent's ztunnel: the load client's card GETs and POSTs at the
      Service address, and the orchestrator's forward. The mock works as a static backend today only because it is
      outside the mesh.
    - The ingress: its namespace is ambient (istio.io/dataplane-mode=ambient), so its plaintext dial of the ClusterIP
      is captured by its own ztunnel. The agent Services carry istio.io/use-waypoint agw-central, so PREDICTED: that
      traffic goes to agw-central (today the ingress dials the pod over HBONE and bypasses the waypoint; note of
      2026-09-09, and httpproxy.rs l.3177 skips the waypoint for ingress unless ingress_use_waypoint). Auto-hostname
      is on by default (httpproxy.rs l.287-299) and rewrites the upstream authority to the backend's host
      (l.4315-4333), so agw-central would match lab/worker or lab/orchestrator. The ingress rows would gain a hop.
  Neither consequence changes how clients address the agents. Both change the topology: at agw-central the agent leg
  leaves the mesh (and fails under STRICT unless the posture changes); at the ingress the path gains agw-central.

## 3. What it does to a request and to the card
  The same A2A block as the marking: the backend's inline A2aPolicy lands in backend_policies.a2a, the field the
  marking's policy fills, and httpproxy.rs l.403-418 (request: classify, a2a.method, protocol a2a) and l.2945-2954
  (response: apply_to_response) read only that field. There is no second A2A code path.
  a2a/mod.rs l.20-43: the card GET's base URL is OriginalUrl or the request URI, through apply_forwarded_scheme
  (crates/http/src/lib.rs l.75-87). l.166-219: the card body is read whole, every supportedInterfaces url rewritten,
  Content-Length removed, the body re-serialised. The scheme source is the downstream request's URI, set in
  normalize_uri (httpproxy.rs l.4288-4310) from the downstream connection's TLS info. The backend has no part in it.
  So PREDICTED from source: at agw-central the card rewrite with the backend type reads https as C-9 measured under
  the marking; at the ingress, http with the Host the client sent. Method recording (a2a.method) and the response
  keys are the same code.
  Main 06c20cef: backend_plugin.go's A2A branch (l.181-197), from_shared (transport_override None, l.4706), the
  Static-to-Opaque conversion (agent_xds.rs l.1865-1871) and the TLS-to-https branch of normalize_uri (l.4561-4584,
  now only when no scheme is set) are unchanged in substance. a2a/mod.rs on main moves the card rewrite into
  rewrite_agent_card through try_modify_body; the base URL still comes from apply_forwarded_scheme. #1829 and #3453:
  not re-read this step (C-9's draft names them).

## 4. The connection count (C-9's 6 per agent, where C-10 counted 1)
  What the proof counted: strict/legs.csv in C-9's run, ztunnel's istio_tcp_connections_opened_total, destination
  reporter, source principal agw-central: 6 to the worker, 6 to the orchestrator. Three work items per Service crossed
  agw-central in the proof (the clean one and two trace ones); only their card GETs reached the agents.
  From source, nothing in the A2A block opens a connection of its own. It makes no request (a2a/mod.rs: classify on
  the request, rewrite on the response). The card body is read to its end (json.rs l.58-66 ->
  crates/http/src/lib.rs l.33-35, axum to_bytes), so the pooled upstream connection is released after it as after
  any complete body. The pool key is (target, resolved address, connection config, HTTP version)
  (client/mod.rs l.231, l.704); the marking does not change any of the four for a Service backend. The pool drops an
  idle connection after 90 s by default (lib.rs l.335-337).

  marking. C-9's proof ran its trace step 13 min 46 s with failed work items, so its card GETs were spaced further
  apart than C-10's. A new upstream connection per card GET would give 3, not 6, so the hypothesis does not by itself
  explain 2 per card GET; that half is open and is what Step 2.1 reads line by line (ztunnel's connection lines at the
  agent, joined on stamps to agw-central's card GET lines).
  Falsified if: with the marking on and card GETs sent close together (well inside 90 s), the counter still rises by
  more than it does unmarked for the same sends.
