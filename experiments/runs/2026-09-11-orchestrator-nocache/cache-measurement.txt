cache-measurement.txt -- why `make orchestrator-image` builds without the layer cache, and what the
cache does and does not do to the two floating inputs. Re-taken on 2026-09-11 in branch followups-5
on the tree at main 8d915b9, before any file of the branch changed the build.
Host: arm64 darwin, docker 29.7.2, buildx v0.36.1-desktop.1.

THE CONTROLLER'S FINDING, AS BRIEFED, AND WHAT IT BECAME
Briefed: `docker build --pull` re-resolves ghcr.io/astral-sh/uv:latest to the registry's current
digest (b485bd65..., uv 0.12.13) but serves the COPY --from step and everything after it from the
layer cache, so the image keeps uv 0.12.12; with --no-cache the builder prints uv 0.12.13; the rootfs
stage's dnf RUN is likewise served from cache until the Amazon Linux base digest moves.
Found: the uv half does not hold. The resolved digest is part of the COPY --from step's cache key; the
CACHED lines a --pull build shows are hits on a layer that was itself built from b485bd65..., which
holds uv 0.12.13 (facts 2 and 3 below), and the image main ships was built by uv 0.12.13
(experiments/runs/2026-09-10-orchestrator-al2023/uv-correction.txt, corrected in commit 25adf5f).
The dnf half holds: a RUN's cache key is its parent layer and its command text, with no repository
state in it (fact 4). That is the reason for --no-cache, by the author's ruling of 2026-09-11.

FACT 4 -- the dnf RUN is a cache hit while the base digest stands still
Not re-run by the builder-target builds above, which stop before the rootfs stage. The committed record:
experiments/runs/2026-09-10-orchestrator-al2023/build.txt, build started 2026-09-10T21:45:55Z, `docker
build --pull`, base resolved to the same digest as the build that last ran the stage (21:29:41Z):
  #5 resolve public.ecr.aws/amazonlinux/amazonlinux:2023@sha256:a0646b8bd35abf5ca3ab94d8cdb5691b9024e19c357531eeefd0ac4762836438 done
  #16 [rootfs 2/2] RUN dnf -y --installroot=/rootfs --releasever="$(rpm -q --qf '%{VERSION}' system-release)" ... upgrade ...   (command shortened here)
  #16 CACHED
  The cache key of that RUN is its parent layer (the base, by digest) and its command text. Nothing
  in it moves when the AL2023 repositories publish a package, so a cached build keeps whatever the
  RUN installed the last time it ran. Not measured: an instance of a package update missed that way;
  the last time the RUN ran before this branch (2026-09-10T21:29:41Z) `dnf upgrade` printed "Nothing
  to do." What this branch's --no-cache build installed and upgraded is in build.txt beside this file.
