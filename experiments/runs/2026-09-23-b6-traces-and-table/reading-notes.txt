TWO THINGS THAT WENT WRONG IN THIS STEP'S OWN TOOLS, KEPT BECAUSE THEY ARE THE SAME LESSON AS B-5a's
  * The FIRST run of tracker-search.sh recorded "0 results" for all seven a2a-python queries. They were not
    empty: the search API allows 30 requests a minute, each query here costs two, and the quota had been spent
    -- a rate-limited query returns an empty page that is indistinguishable from a genuine "nothing found".
    The driver was rewritten to read `gh api rate_limit` before every call, wait for the window, and record any
    call that still fails as FAILED rather than as 0. The committed file is the re-run, 0 failures, and the
    a2a-python queries return, in query order, 20, 20, 18, 20, 20, 2 and 0 results. Had the first take been
    committed, this step would have concluded "nothing new upstream" from an artefact, which is B-5a's mistake
    in another dress.
  * items-read.sh first reported "(none found)" for every merged pull request's release containment. Two causes,
    both fixed and both commented in the script: `gh` inside a `while read` loop consumed the loop's own stdin,
    and under `set -o pipefail` a `grep -q` that matches early kills `gh` with SIGPIPE, so the pipeline returned
    141 and every release read as "does not contain". The committed run is after both fixes; the containments it
    reports were each spot-checked by hand against `gh api compare`.

A THIRD THING THAT WENT WRONG IN THIS STEP'S OWN TOOLING, RECORDED RATHER THAN QUIETLY FIXED
  The first version of own-keepawake-lines.txt was written by a `{ echo ...; } > file` block, and one of its
  echo lines carried a backtick pair inside DOUBLE quotes. The shell ran it as a command substitution, so
  `pmset -g log` executed and its whole output -- the host's week of power history, with every line's text --
  landed in that file: 11 656 857 bytes. It is a READ; nothing on the host was changed, no keep-awake was
  started and no power setting was touched. The file was deleted before anything was staged, was never
  committed, and the directory was then scanned for any remaining power-log text: the only file that matches
  those words is sleep-events.sh, which names the four kinds it keeps in its own comments and is B-4's script
  byte-identical. own-keepawake-lines.txt is now written by count-own-keepawake.sh, a committed script with no
  interpolation in any printf format.
  This is the same mistake B-3 made with an unquoted heredoc, in another dress, and against the brief's own
  third standing rule. The rule is not "use `<<'EOF'` for heredocs"; it is that nothing this lab writes may run
  what it means to print. Every other note in this directory was written through a quoted heredoc or printf,
  which is why this one is the only one that ran anything.

ONE POST-PROCESSING STEP ON items-read.txt, NAMED SO THAT IT IS NOT MISTAKEN FOR THE SCRIPT'S OUTPUT
  GitHub returns issue and pull-request bodies with CRLF line endings, and the quoted body excerpts in
  items-read.txt carried them. The committed file is the 23:25Z run with those carriage returns stripped
  afterwards (`tr -d '\r'`); items-read.sh now does that itself, at the line it is commented on, so a re-run
  reproduces the committed file apart from its own read stamps. The run was not repeated, because the two
  upstream drafts cite that run's stamps and a fresh read would have moved them for no gain. Nothing but the
  carriage returns was touched: no state, no date, no count. The same normalisation is why table.py and
  trace-census.py now pass `lineterminator="\n"` to their CSV writers -- this repository's committed CSVs are
  LF, and `core.autocrlf=input` would otherwise have committed something other than what is on disk.
