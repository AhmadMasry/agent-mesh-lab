Nothing this lab counts reads a locale, and that is measured rather than assumed:

================================================================================
2. WHICH PACKAGES STILL CLAIM THE TREES THE rootfs STAGE REMOVES BY PATH
================================================================================

The Dockerfile header states that whole packages leave through `rpm -e` so that the RPM
database and the filesystem make one statement. That holds for bash and coreutils. It does
not hold for the content trees the same RUN prunes with `rm -rf`, and this is the
measurement of exactly where it stops.

METHOD, and it differs from the pushed one in a way that corrects it. The pushed file fed
the 45 package names to `rpm -ql` inside a throwaway container of the base tag, which
answers from THAT container's own database -- so a package the base image does not carry,
python3.14 among them, silently returned nothing. Here the throwaway container of the same
base tag reads the assembled root's OWN database instead: only /var/lib/rpm is copied out
of the image (`docker create` + `docker cp`) and rpm is pointed at it with
`rpm --root=<dir> -ql <pkg>`. The assembled root has no rpm binary of its own; this is the
database it ships. 45 names, gpg-pubkey dropped. No rebuild, no cluster.

Result, one line per prefix the rootfs stage removes, plus /usr/lib/locale which it no
longer removes:

  /usr/lib/locale    filesystem glibc-common
  /usr/share/locale  filesystem glibc-common grep p11-kit sed
  /usr/share/man     alternatives ca-certificates crypto-policies expat filesystem grep libcap p11-kit pcre2-syntax python3.14 sed
  /usr/share/doc     ca-certificates expat filesystem gmp grep libcap libffi libtasn1 ncurses-base p11-kit pcre2-syntax python3.14 python3.14-libs sed setup sqlite-libs tzdata zlib
  /usr/share/info    filesystem grep readline sed
  /etc/yum.repos.d   amazon-linux-repo-cdn system-release
  /etc/dnf           amazon-linux-repo-cdn system-release
  /var/lib/dnf       (none of the 45)
  /var/cache         filesystem glibc
  /var/log           filesystem setup

Two attributions the pushed table got wrong, corrected by reading the shipped database:
`python3.14` claims paths under /usr/share/man and /usr/share/doc, and `python3.14-libs`
under /usr/share/doc. Everything else agrees line for line, /var/lib/dnf included: it is
claimed by none of the 45, `dnf-data` never having been installed into this root, so
removing it removed nothing any package claims.

/usr/lib/locale is the line that changed. It is claimed by `filesystem` (the directory)
and by `glibc-common` (the directory, C.utf8, LC_MESSAGES and the 12 files) -- 15 paths
between them -- and all 15 are now present. Counted over the whole root:

  paths claimed by the 45 packages in the shipped database : 5546
  of those, absent from the image                          :  261
    /usr/share/locale  156     /etc/dnf            6     /var/cache        3
    /usr/share/doc      56     /usr/share/info     5     /etc/yum.repos.d  2
    /usr/share/man      28     (other)             5     /var/log          1
  the same count while /usr/lib/locale was removed         :  276

("other" is /etc/fstab, /etc/gai.conf, /etc/crypto-policies/state/CURRENT.pol and
/usr/lib64/python3.14/email/architecture.rst -- three configuration files the install
never wrote and one document `--setopt=tsflags=nodocs` left out. `basesystem` and
`glibc-minimal-langpack` own no files at all, so rpm prints "(contains no files)" for
them; that line is not a path and is not counted.)

So keeping the archive takes the claimed-but-absent count from 276 to 261: the database
and the filesystem agree about 15 more paths than they did, which is a smaller version of
the same argument the header makes for `rpm -e` over `rm`. The remaining 261 are the
trees above, and three things bound what they cost, unchanged by this amendment. The
packages involved cannot be erased: they are `filesystem`, `glibc-common`,
`system-release`, `grep`, `sed`, `ca-certificates`, `python3.14` and the like -- what the
interpreter and the distribution identity are built on -- so what is removed is their
content, not their entry. No package VERSION is falsified, and a version is what a package
scanner matches on, so the scan of this image counts what is really installed
(scan/orchestrator.json identifies it as amazonlinux 2023). And nothing inside the image
can act on the difference: there is no rpm, no dnf and no microdnf binary here, and no
shell to drive one.

Much of the man/doc/info/locale content was never installed in the first place: the
install carries `--setopt=tsflags=nodocs`. The `rm -rf` is there to take whatever nodocs
does not, and the table above is about which packages CLAIM those paths, not about how
many bytes the removal actually took.
